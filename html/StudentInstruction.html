Never run two timing binaries in the background at the same time bound to overlapping taskset cores — they'll contend with each other and corrupt both measurements without any warning.

Part 2: Keeping Claude in Bounds

This is a pedagogic project. The goal is not a working kernel — it's you learning to design and run an experiment yourself. Handing control over to Claude solves the programming task and teaches you nothing.

Don't do any of the following ways to inadvertently transfer control to Claude:

  • Auto-accept / bypass-permissions mode, or running Claude as an unsupervised background/looped agent.
  • Granting blanket permission you don't actually have.
  • A --dangerously-skip-permissions-style launch flag, or a session-wide "bypass permissions" mode set at the start rather than approved per step.
  • An overly broad permissions.allow entry (e.g. a wildcard covering a command that itself wraps arbitrary execution) in .claude/settings.json / settings.local.json — including one copied from someone else without understanding what it allows.
  • Running the session as root, or inside a container/environment with broader access than intended.
  • Connecting an MCP server with powerful capabilities without reviewing what it can do.
  • A personal, upstream CLAUDE.md (global, or a parent directory's) written for other coursework, whose permissive instructions apply here without you realizing it.
  • Telling Claude a prior step was "already approved" while reconciling out-of-date records, instead of pointing to actual evidence for it.
  • Asking Claude for a brief recommendation and a yes/no — every step gets approved, but Claude ends up originating the design, not you.
  • Letting Claude propose or implement multiple alternative variants/strategies to explore in parallel, instead of testing one hypothesis at a time — that's not the scientific method this course is built on.
  • Letting Claude resolve an undocumented-convention question on its own judgment instead of checking with you or the instructor first.
  • Trusting Claude's summary of a change instead of reading the actual diff/code — Claude may not obey your instructions exactly, even when specific.

How this is enforced, not just written down: this project's .claude/settings.json backs some of these rules with real restrictions, not just a written policy:

  • defaultMode: "default" — every Edit/Write/Bash still prompts you individually; there's no way for a blanket approval to sneak in from this project's own settings.
  • disableBypassPermissionsMode: "disable" — a --dangerously-skip-permissions-style launch is unavailable in this project, not just discouraged.
  • deny: ["Bash(sudo *)"] — sudo is blocked outright, regardless of what else gets approved.

If any of this ever needs loosening to get something done, that's a signal to stop and ask the instructor — not to edit the json yourself.

Running a Single Call Yourself

sweep.sh builds, gates, and then calls the timing binary with this exact invocation. You can run the same command directly in your terminal for a one-off timed call, skipping the build/gate/csv steps:

# sequential (t=1), pinned to one core:
taskset -c 16 ./bin/PolyMult.time -dA <int> -dB <int> -t 1 -r <int>

# parallel (t>1), bound and placed:
OMP_PROC_BIND=close \
OMP_PLACES='{16},{20},{24},{28},{17},{21},{25},{29},{18},{22},{26},{30},{19},{23},{27},{31}' \
taskset -c 16-31 ./bin/PolyMult.time-par -dA <int> -dB <int> -t <range> -r <int>

The core list, pinned sequential core, and OMP_PLACES string are _gate.sh's current defaults (BPM_CORESET, BPM_SEQ_CORE, BPM_OMP_PLACES) — check there if they've been overridden for a different machine. taskset plus OMP_PROC_BIND/OMP_PLACES together give you a precise, repeatable mapping of threads to cores; without them, the OS scheduler and OpenMP runtime are free to place threads differently from one run to the next, including onto fewer cores than intended, which corrupts the measurement.

Where Results and Plots Land

  • sweep.sh writes each call's csv under its own <variant-dir>/results/.
  • plot.py's output path auto-derives: csvs from a single variant produce a workbook inside that variant's own ./plots/<topic>/; csvs spanning more than one variant produce a cross-variant comparison workbook one level up, in ../plots/<topic>/ at the common parent.

T(seq): What the Baseline Actually Is

Each variant's Speedup is computed against the minimum of up to three things: its own no--fopenmp binary's time, its *Q ancestor's own no--fopenmp binary's time (a *P<n> variant may restructure the loop nest, not just annotate it — so these can genuinely differ), and this sweep's own 1-thread time. Whichever is smallest wins. Every variant, including every *P<n> parallel one, needs its own --record-seq — recording never happens automatically across directories, only the lookup does.

This makes Speedup an approximation, not a number you should compare precisely across variants — Performance is the metric for that.
