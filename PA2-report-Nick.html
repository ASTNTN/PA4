PA2 Report: Parallelizing and Vectorizing the Outer Product

Name: Nick Hinderer  ·  Date: 2026-10-01  ·  Machine: tuna (i9-13900K, E-cores only, Turbo off)

Starting Point

The kernel is c[i+j] += a[i] * b[j] over the whole (i, j) rectangle. All headline timing is at 100,000 × 100,000 (1010 multiply-adds, 20 GFLOP); two lopsided shapes with the same work, 4,000,000 × 1,000 and 1,000 × 4,000,000, are used wherever the shape matters. Peak (TPP) is 35.2 GFLOP/s per E-core. Sequential runs are pinned to core 16. Parallel runs use _gate.sh's binding: cores 16–31, OMP_PROC_BIND=close, cluster-cyclic places (first four threads on four different clusters, then the second core of each, and so on). Every variant passed the shared gate (42 oracle cases, 14 gold cases, sequential and parallel binaries) before any timing. Hardware counters are from perf stat --cputype cpu_atom, normalized per useful 8-wide FMA (one vector FMA = 16 flops).

Background: what an FMA is, and why everything is counted per FMA

The whole computation is one pattern repeated 10 billion times: multiply one coefficient of a by one of b and add the result into c. A fused multiply-add (FMA) instruction does that multiply and add together, and the 256-bit version does it for 8 numbers side by side. So one vector FMA is 8 multiply-adds, which counts as 16 floating-point operations: 8 multiplies and 8 adds.

An E-core can finish at most one vector FMA per clock cycle. At 2.2 billion cycles per second that is 2.2 × 16 = 35.2 GFLOP/s, the peak (TPP) used throughout.

That makes cycles per vector FMA a convenient yardstick: 1.0 means running at peak, 2.0 means half of peak. The other counters are divided the same way, so "4 load µops per vector FMA" reads as: for each unit of useful work, the core did four of those.

OPQ's inner loop is vectorized (one vmovups of b, one vfmadd213ps with c as a memory operand, one vmovups store per 8 floats). Each 256-bit load or store costs two µops on an E-core, so the loop needs about 9 µops per FMA against an allocation width of 5 per cycle. GSQ is slower for a different reason: its anti-diagonal dot product is one dependent FMA chain, which caps it at 16 flops per 6-cycle FMA latency, 5.87 GFLOP/s; it measures 5.61.

Background: µops, and the limit of 5 per cycle

A core does not execute instructions directly. It first breaks each one into micro-operations (µops), small steps it can schedule on their own. An E-core's internal machinery is 128 bits wide, so any 256-bit load, store or arithmetic instruction becomes two µops, one for each half.

The core can accept at most 5 µops per cycle. That limit is separate from how fast it can compute: a loop that needs 9 µops for each vector FMA cannot finish an FMA more often than every 9/5 = 1.8 cycles, even if all its data were instantly available.

Background: latency and throughput, and why GSQ is slow

Two different speeds describe an FMA. Throughput: the core can start a new one every cycle. Latency: each one takes 6 cycles to produce its result. The two don't conflict as long as the FMAs are independent, the way a production line can start a new item every minute although each takes an hour to finish.

GSQ computes each c[k] as a running sum. Every FMA adds to the result of the one before, so it cannot start until that result exists. The core then completes one FMA per 6 cycles instead of one per cycle, and 16 flops every 6 cycles is 5.87 GFLOP/s. OPQ doesn't have this problem, because each of its FMAs updates a different element of c.

Experiment 1: which polynomial is the inner loop (OPQ vs EXQ)sequential

Question

OPQ and EXQ do identical work in a different loop order. Does the order matter, and if so is it the cache level the inner loop's window lives in?

Hypothesis

Per outer iteration the inner loop sweeps a window of the inner operand and a window of c of the same length L: about 8L bytes. The rate should step down as 8L crosses L1 (32 KB, L ≈ 4,000), the cluster's L2 (4 MB, L ≈ 500,000) and L3. EXQ should be OPQ's mirror image with dA and dB exchanged, because swapping the loops swaps which operand is inner.

Background: caches, and why speed should drop in steps

Data the core used recently is kept in small, fast memories called caches. An E-core has its own L1 (32 KB, reached in about 5 cycles). Behind it is an L2 (4 MB, about 15 cycles) that it shares with the three other cores of its cluster, then an L3 (36 MB, about 50 cycles) shared by the whole chip, then main memory (200–300 cycles).

On every pass of its inner loop this program sweeps a stretch of one polynomial and an equally long stretch of c. If those two stretches fit in L1, every pass finds its data already there. If they don't, each pass has to fetch them again from the next level, and the loop runs at the speed of that level. So the rate should drop in steps as the inner loop gets longer, one step for each cache level outgrown.

Experiment Design

12 shapes at constant work (≈ 4·109 multiply-adds), inner length 1,000 to 4,000,000, in both orientations; GSQ as a control (its access pattern does not depend on which polynomial is longer). sweep.sh --threads 1 --reps 3 --record-seq, core 16. Counters on OPQ and EXQ at 4M × 1K and 1K × 4M.

Experiment Run

tuna, one sweep at a time. Results: 01-OPQ/results/*_cache_*.csv, 02-EXQ/results/*_cache_*.csv, 00-GSQ/results/*_cache_*.csv.

Supported, including the mirror. The knee positions match 8L against L1 and L2. For every later variant the lesson is: keep the inner window (and the part of c it touches) inside L1, whatever the shape. Neither OPQ nor EXQ is "better"; the one whose inner operand is shorter wins.

Experiment 2: outer loop with an array reductioncoarse grain

Question

The simplest race-free way to split OPQ's i loop across threads is to give every thread its own copy of c. How far does that scale?

Background: the race, and what a reduction does about it

Adding into c[k] is three steps: read the old value, add, write the new value. Row i of the outer product adds into c[i], c[i+1], … and row i + 1 adds into c[i+1], c[i+2], …, so different rows update many of the same elements. If two threads run different rows at the same time, both can read the same old value of some c[k], each add its own product, and each write back. One of the two additions is lost. That is a race, and it gives wrong answers that change from run to run.

A reduction avoids it by giving every thread its own private copy of c, starting at zero. Each thread adds only into its own copy, so nothing collides, and when the threads finish, the copies are added together into the real c.

Hypothesis

Close to linear. The private copies remove the race, and zeroing and merging t copies of c costs on the order of n·t operations against n² for the multiply.

Experiment Design

#pragma omp parallel for schedule(static) reduction(+:c[:n]) on the i loop; under -DCHECKING the Kahan array comp is reduced too. Kept as 01-OPP1/attempts/reduction.c. 100K × 100K, threads 1–17, 3 reps.

Experiment Run

Gate passed (both binaries, 16 threads). Timed with the time-par binary directly, same binding as sweep.sh.

Experiment 3: own the output, in small blocks dealt out dynamicallycoarse grain

Question

If c is cut into blocks and each block belongs to exactly one thread, there is no race and no reduction, and a block of ~2,000 outputs keeps its c and the matching b window in L1 for the whole i loop. Does that scale linearly?

Hypothesis

Single-thread speed rises to the L1 plateau of Experiment 1 (~13 GFLOP/s) and, with nothing shared and little L2 traffic, speedup is close to linear at all thread counts. Blocks are dealt with schedule(dynamic, 1) because the work per block is a trapezoid in k.

Experiment Design

For each block [lo, hi]: zero it, then for every i that reaches it, run the OPQ inner loop over the j's that land in the block. Block size is a runtime knob (--tune block_size). Two versions: block edges at arbitrary offsets (attempts/owner_unaligned.c) and edges on 64-byte lines of c (attempts/owner_dynamic_blocks.c). 100K × 100K, threads 1–16, 3 reps; a block-size scan at 1, 2, 4, 16 threads; counters at 1 vs 2 threads.

Experiment Run

Gate passed for both. Direct binary runs, same binding.

Analysis

  • One thread reaches 13.9 GFLOP/s, as predicted (1.47× OPQ). Scaling does not: 2 threads give 19.1 (unaligned) and 21.3 (aligned) instead of 27.8, and 16 threads give 139.1 and 147.7.
  • Line-aligned edges help a little, so false sharing on the shared boundary line is real but small.
  • Block-size scan (aligned edges, GFLOP/s at 1 / 2 / 16 threads): 256: 12.0 / 12.7 / 53; 512: 13.6 / 15.1 / 93; 1024: 13.2 / 17.2 / 112; 2048: 13.9 / 21.7 / 147; 4096: 13.2 / 24.3 / 162; 8192: 9.9 / 19.1 / 42. Smaller blocks (more boundaries) scale worse; at 8192 the block no longer fits L1.
  • Counters, block 1024, one thread vs two (cores 16 and 20), same instructions (24.4 G): cycles 9.96 G → 15.3 G; loads missing L1 2.6 M → 77 M; loads missing L2 32 K → 9.4 M; load-stall cycles 27 M → 1.98 G; memory-ordering machine clears 15 → 1.65 M.

Conclusions

Partly supported: blocking for L1 works, dynamic dealing does not scale. The two-thread counters show coherence traffic (lines invalidated under a thread, refetched from L3, machine clears) even though no output line is written by two threads after alignment. The likely cause is that two threads always work on neighbouring blocks and the hardware prefetchers, streaming ahead of one thread's block, pull in lines the neighbour is writing. Disabling the prefetchers to prove it is not possible without root, so this stays an inference; Experiment 4 tests its prediction that fewer boundaries fixes the scaling.

Background: how threads slow each other down without sharing data

Each core keeps its own copies of the cache lines (64-byte pieces of memory) it is using. When one core writes to a line, every other core's copy of that line is thrown away and has to be fetched again. This is how the hardware keeps the cores consistent, and it happens whether or not the cores care about the same bytes.

False sharing is two threads writing different values that happen to sit in the same 64-byte line: the line bounces between their cores although they never touch the same data. A prefetcher can cause a milder version. It fetches data ahead of where a thread is working, and if it runs into memory a neighbour is writing, lines get pulled back and forth.

When a line is taken away after a core has already used it for work in progress, the core has to throw that work away and redo it. The counter for that is the machine clear.

Experiment 4: one contiguous, work-balanced range per thread (final OPP1)coarse grain

Question

If each thread owns one contiguous range of c, there are only t − 1 boundaries instead of hundreds. Does speedup become linear?

Hypothesis

Yes: 16 threads at ≥ 15× their own single-thread rate at every shape, with no drop when a cluster doubles up (each thread's working set is in L1, so the cluster L2 carries almost nothing). 17 threads should drop sharply: a static split makes every thread wait for the two that share a core.

Experiment Design

01-OPP1. The design has five parts.

1. What a thread owns. Each product a[i]*b[j] is added into exactly one output, c[i+j]. A thread is given a range of outputs c[Kt … Kt+1 − 1] and is the only thread that adds into them. Every product belongs to one output and every output to one thread, so each product is added exactly once and no two threads write the same c[k]. No reduction or private copy is needed.

2. How much work is in each output. The pairs that add into c[k] have 0 ≤ i ≤ dA and 0 ≤ k − i ≤ dB, so i runs from max(0, k − dB) to min(k, dA):

w(k) = min(k, dA) − max(0, k − dB) + 1

This climbs 1, 2, 3, … until k reaches the shorter degree, stays flat until k reaches the longer one, then falls back to 1. Equal-width ranges of c therefore hold unequal work. At 100K × 100K with 16 threads, the middle threads would get 11.7% of the work each and the end ones 0.8%.

3. Where to cut. Let W(K) be the number of pairs landing in outputs below K. With m = K − 1:

W(K) = K + S1 − S2

S1 = m(m + 1)/2                      if m ≤ dA
   = dA(dA + 1)/2 + (m − dA)·dA      if m > dA

S2 = 0                               if m ≤ dB
   = (m − dB)(m − dB + 1)/2          if m > dB

The total is W(dA + dB + 1) = (dA + 1)(dB + 1). With T threads, thread t starts at the smallest K with W(K) ≥ (t/T) × total. W only increases with K, so K is found by binary search, 18 steps for 200,001 outputs. (A direct formula exists, K ≈ √(2 × target) in the rising part, but it has three cases; the search handles all of them.) Each boundary is then moved to the nearest cache-line boundary of c, so no line is written by two threads.

4. Example, 100K × 100K, 4 threads.

5. Inside a range. The thread finishes one block of 2,048 outputs before starting the next:

for (klo = first; klo < last; klo += 2048) {         /* one block */
    lo = klo;  hi = min(klo + 2048, last) - 1;
    zero c[lo .. hi];
    for (i = max(0, lo - dB); i <= min(dA, hi); i++)       /* rows that reach it */
        for (j = max(0, lo - i); j <= min(dB, hi - i); j++)  /* j's that land in it */
            c[i + j] += a[i] * b[j];                 /* OPQ's statement */
}

For one block, row i reads b[lo−i … hi−i] and updates c[lo … hi], 8 KB each, and the next row uses the same data shifted by one float. About 16 KB stays in L1 at any problem size.

Experiment 6: one core toward TPP (OPP2)fine grain

Question

How close to 35.2 GFLOP/s can the outer product get on one E-core, and what stops it?

Hypothesis

TPP means one vector FMA finishing every cycle. An E-core can start one vector FMA per cycle, but it can also start only one 256-bit load per cycle (Procinfo2 § 1.A, Procinfo3 § 2.D). OPQ's statement c[k] += a[i] * b[k−i] needs two loads for every FMA, one of b and one of c, plus a store of c. So even with all data in L1, OPQ can finish an FMA only every 2 cycles: 50% of TPP.

Background: ports, and why loads can set the speed

Inside a core, each kind of work is started at its own ports, and a port can start one thing per cycle. An E-core has two ports for floating-point arithmetic and two for loads, each 128 bits wide. A 256-bit FMA needs both arithmetic ports and a 256-bit load needs both load ports, so the core can start exactly one of each per cycle.

The scarcest port sets the speed. A loop that needs two 256-bit loads for every FMA keeps the load ports busy for two cycles per FMA, while the arithmetic ports sit idle half the time. The only way to speed it up is to need fewer loads.

The goal is therefore fewer loads per FMA. The load of b can't be avoided, since every product needs a different piece of b. The load and store of c can: if R rows are added into c[k] while it sits in a register, c is loaded and stored once per R FMAs. That leaves (R + 1)/R loads per FMA. With R = 8 that is 9/8, which allows 8/9 = 89% of TPP.

Hypothesis: with R = 8, loads per FMA fall from 2 to about 9/8 and the rate rises toward 89%. Split loads and the 6-cycle latency of the FMA will have to be dealt with for that ceiling to be reachable.

Experiment Design

OPP2 keeps OPP1's ranges and blocks, because the data has to stay in L1 for any of this to matter (Experiment 1). It changes only the loop inside a block, in two ways.

Unroll-and-jam: so that c stays in a register. In OPQ, row i sweeps the whole block before row i + 1 touches the same c[k], and by then c[k] has long since been written back to memory.

for (i = ilo; i <= ihi; i++)               /* one row at a time */
    for (k = lo; k <= hi; k++)
        c[k] += a[i] * b[k - i];           /* load c, load b, FMA, store c */

To add 8 rows into c[k] while it is still in a register, the 8 rows have to be handled together. Take 8 rows per pass of the outer loop (unroll), and fuse their 8 inner loops into one (jam):

for (i0 = ilo; i0 <= ihi; i0 += 8)         /* 8 rows per pass */
    for (k = lo; k <= hi; k++) {           /* their inner loops, fused */
        c[k] += a[i0]     * b[k - i0];
        c[k] += a[i0 + 1] * b[k - i0 - 1];
        ...
        c[k] += a[i0 + 7] * b[k - i0 - 7];
    }

Vectorized 8 wide, c[k … k+7] is loaded once, receives 8 FMAs and is stored once: 9 loads and 1 store per 8 FMAs, where OPQ needed 16 loads and 8 stores. The eight values of a are each copied into all 8 lanes of a register before the loop, which is why R can't grow freely: those R registers and the registers holding c must all fit in the 16 the core has.

Four aligned copies of b: so that no load is split. Removing loads isn't enough if the remaining ones are slow. Row i reads b starting at b[k − i], so the 8 rows start one float apart, at 8 different alignments. A 256-bit load that straddles a 64-byte cache line is a split load and takes two cycles instead of one (Procinfo3 § 2.D). OPQ has 0.375 of them per FMA. A single copy of b can't be aligned for all 8 rows at once. So OPP2 keeps four copies, shifted by 0, 1, 2 and 3 floats, each starting on a cache-line boundary, and every row reads from the copy in which its window starts on a 16-byte boundary. The cost is three extra copies of b, built once per call.

Background: split loads, and why four copies fix them

Memory is organized in 64-byte cache lines. A 256-bit load reads 32 bytes, and if those bytes lie across the boundary between two lines the core has to do the read in two parts. That is a split load, and it takes about twice as long. More precisely, the E-core reads in 16-byte halves and a load is split when one half straddles a boundary, so a load that starts on a multiple of 16 bytes is never split.

In this loop row i reads b starting at b[k − i]. Each next row starts 4 bytes later, so whatever the alignment of one row, the others are off. With four copies of b, each shifted by one more float, every row can find a copy in which its reads start on a 16-byte boundary.

That was the plan. Timing is at 100K × 100K on core 16. After each version the counters and the assembly of the inner loop were read, and what they showed decided the next step.

Experiment Run

All versions pass the gate (both binaries). The timed build of the final version was also checked by 01-OPP2/tools/verify_time.c (162 configurations, no failures). The first two versions are kept as 01-OPP2/attempts/v1_reassociated.c and v2_fma_chain.c. Steps 1 to 3 were run on 2026-10-01. The table that separates step 3's two changes, and the R = 10 and R = 12 numbers with counters, were measured on 2026-10-09.

Analysis

Step 1: unroll-and-jam with R = 8, plus the aligned copies. 20.30 GFLOP/s, 57.7% of TPP, up from 14.03. The loads did what the hypothesis says: load µops per FMA fell from 4.02 to 2.30 (2 µops per 256-bit load, so 1.15 loads), and split loads fell from 0.375 per FMA to zero. But 57.7% is far from 89%. Background: how to read a line of this listing

Each line is one instruction. Take vfmadd231ps (%r14,%rax,1),%ymm11,%ymm1.

vfmadd231ps is the operation: a fused multiply-add on 8 single-precision numbers. vmulps is a multiply, vaddps an add, and vmovups a copy to or from memory.

%ymm11 and %ymm1 are vector registers, each holding 8 floats. The last one named receives the result, so this line computes ymm1 = ymm1 + ymm11 × (the first operand).

(%r14,%rax,1), in parentheses, is a read from memory at the address r14 + rax. Here it is 8 floats of b.

So this single line loads a window of b, multiplies it by a value of a held in ymm11, and adds the result into ymm1. Counting the lines that start with vfmadd, vmul or vadd gives the number of floating-point operations per pass of the loop.

That is 4 multiplies, 4 FMAs and 4 adds: 12 floating-point operations for 8 multiply-adds of work. -ffast-math lets the compiler regroup a sum, and it regrouped the 8 products into pairs. This was not expected. Since the core does one 256-bit floating-point operation per cycle, this loop can't beat 8/12 = 67% whatever its loads do.

Background: FMAs, and what -ffast-math changes

A fused multiply-add (FMA) computes a × b + c in a single instruction. This loop's work has exactly that shape: multiply a value of a by a value of b and add the product into c. Done as FMAs, each multiply-add costs the core one operation.

In floating point the order of additions matters slightly: (x + y) + z does not always round to the same bits as x + (y + z). So a compiler normally keeps the order the program wrote. -ffast-math lifts that rule and lets it regroup sums in whatever way it estimates is faster.

The program adds eight products into c one after another. The compiler regrouped them into pairs, (p0 + p1) + (p2 + p3) and so on, which shortens the wait between additions that depend on each other. But only one product of each pair can be folded into an FMA. The other needs a multiply of its own, and joining the pairs needs separate adds. The answer is the same up to rounding, with 12 operations where 8 would do. On a core that completes one such operation per cycle, that alone holds the loop to two-thirds of its possible speed.

Step 2: keep the chain of FMAs. To get the eight FMAs back, the function holding the loop is compiled with optimize("no-associative-math"). Only that function, so everything else stays under the harness's -ffast-math. The loop becomes what was intended:

vmovups     (%r14,%rax,1),%ymm0              ; b window, row 0
vfmadd213ps (%rcx,%rax,1),%ymm8,%ymm0        ; × a[i0], + c[k..k+7] from memory
vfmadd231ps 0x0(%r13,%rax,1),%ymm7,%ymm0     ; + a[i0+1] × b window, row 1
vfmadd231ps (%r12,%rax,1),%ymm6,%ymm0
vfmadd231ps (%rbx,%rax,1),%ymm5,%ymm0

vfmadd231ps (%r10,%rax,1),%ymm3,%ymm0
vfmadd231ps (%r9,%rax,1),%ymm2,%ymm0
vfmadd231ps (%rdx,%rax,1),%ymm1,%ymm0        ; + a[i0+7] × b window, row 7

23.62 GFLOP/s, 67.0%. With 1.15 loads per FMA this loop could run at 87%, so something other than loads is holding it back. The counters showed two things:

  • FMA latency. The FP scheduler, where FMAs wait for their inputs, is full for 41% of the slots. All 8 FMAs write the same register, so each waits 6 cycles for the one before it (Procinfo2 § 2.A): 48 cycles per vector of c.
  • L1. 15% of loads miss L1. A block of 2,048 outputs is 8 KB of c plus an 8 KB window in each of the four copies of b: 40 KB, more than the 32 KB of L1. The extra footprint of the copies had not been accounted for.
Background: the FP scheduler, and why interleaving helps

An instruction that has been accepted but can't run yet, because one of its inputs isn't ready, waits in a holding area called a scheduler. Floating-point work has its own. It has a fixed number of places, and when it is full the core stops accepting new instructions.

Here the eight FMAs for one vector of c each need the result of the one before, and each result takes 6 cycles. So most of them are waiting at any moment, and they fill the scheduler. The core is not short of data or of ports. It is waiting for its own earlier results.

The remedy is to give it work that doesn't depend on those results: handle several vectors of c at once and alternate between them. While one vector's FMA is in progress, the core can start the next vector's.

Step 3: interleaved vectors of c, and a smaller block. Both were addressed in the same step. The loop was changed to work on several vectors of c at once, applying row 0 to all of them, then row 1, and so on, so that consecutive FMAs don't depend on each other. With four vectors, a scan of the block size gave 26.6 / 27.5 / 27.9 / 27.0 / 22.9 GFLOP/s at 512 / 768 / 1,024 / 1,536 / 2,048, so the block was set to 1,024 (20 KB). A scan of the number of vectors at that block size gave 26.6 / 28.4 / 27.9 / 28.4 for 2 / 3 / 4 / 6, so three were used. Result: 28.46 GFLOP/s, 80.8% of TPP.

Because both changes went in together, that run doesn't say what each contributed. The four combinations were measured separately afterwards (GFLOP/s):

  • Final: 28.46 GFLOP/s, 80.8% of TPP, 3.0× OPQ. The loop does 1.19 loads per FMA, slightly more than 9/8 because of the ragged ends of each block. That allows at most 84%, so OPP2 is within 4% of what its loads permit.
  • A larger R would lower loads per FMA further, but in the first scans R = 10 and R = 12 were slower (24.6 and 25.7 with four vectors). The later counters show the FP scheduler full again in those builds (52%), and nothing spilled to memory. The R values of a and the vectors of c share 16 registers: R = 12 leaves room for only 4 vectors, while R = 10 with 6 fits exactly and gives 28.8, 1% above the R = 8 setting, which was kept.
  • 4M × 1K: same code, 22.5 GFLOP/s (64%), because the inner loop is only 1,001 long.

Conclusions

Supported in its mechanism: unroll-and-jam brought loads per FMA from 2 to about 9/8, and the aligned copies removed the split loads. Reaching the rate that allows took two things the plan did not include, the compiler regrouping the FMAs and the copies overflowing L1, and one it named only in passing, the latency of the FMA chain. OPP2 ends at 81% of TPP, limited by the one load per FMA that the sliding window of b requires. Experiment 7 tries to get under that.

Experiment 7: fewer than one load per FMA (hand-written tile)fine grain

Question

Can a register tile reuse each b window for several FMAs and beat OPP2?

Hypothesis

With R rows and U vectors of c, the window at offset o feeds every (row r, vector m) with 8m − r = o, which is R/8 FMAs. If a[i] comes in through a broadcast (documented as a single load µop, two per cycle), load µops per FMA fall to about 1 + 16/R: at R = 32, U = 8 the FMA port, not the load port, would be the limit.

Experiment Design

AVX2 intrinsics for the interior tile only (the checking build runs the same block/group/edge control flow with plain BPM_ACC loops, so the timed build was validated separately by verify_time). Empty asm register constraints stop GCC from folding the window load back into every FMA. R in 16–48, U in 6–12, block 1,024–1,536. Kept as 01-OPP2/attempts/v4_intrinsics_window_reuse.c.

Experiment Run

Gated; timed build verified (0 failures). Two versions of the tile were built, 01-OPP2/attempts/v4_intrinsics_window_reuse.c and v5_tile_base_displacement.c, plus a test loop, 01-OPP2/tools/fma_load_mix.c.

Analysis

  • First version: best 22.5 GFLOP/s (R = 48, U = 8, block 1,536), 64% TPP: slower than OPP2.
  • Counters: 5.7 µops and 2.48 load µops per FMA, more loads than OPP2's 2.38. The assembly shows the cause: the compiler kept a separate pointer for each of the 48 rows and reloads one from the stack before nearly every broadcast.
  • With every broadcast addressed from one base register (v5), the reloads are gone and loads fall to 1.63 µops per FMA, but the rate is only 23.4 GFLOP/s.
  • A 256-bit broadcast is one load µop, as documented, but two µops in all. In a test loop, one 256-bit broadcast per FMA slows a stream of FMAs from 1.00 to 1.31–1.34 cycles per FMA, where one 256-bit load per FMA does not slow it at all. The tile has one broadcast per FMA.
Background: what a broadcast is, and why the tile needs so many

A broadcast takes one number and copies it into all 8 lanes of a vector register, so that 8 different values of b can each be multiplied by the same value of a. OPP2 does its eight broadcasts once, before the inner loop, and keeps the results in registers. The tile uses far more values of a than there are registers, so it repeats a broadcast from memory for every FMA.

Reading the 4-byte number is cheap for the load ports. Spreading it across 256 bits is a second step, and the test loop shows that doing one for every FMA slows the FMAs themselves. The tile saves loads and pays for them in the arithmetic.

Conclusions

Refuted. The loads did fall below one vector load per FMA, but each FMA then needs its own broadcast, and on this core that costs more FMA throughput than the loads it saves. OPP2's arrangement, with the broadcasts held in registers and the windows read from memory, remains the fastest measured.

Experiment 8: EXP2, and both tuned kernels on 16 corescoarse + fine grain

Question

Does the EXQ order reach the same single-core rate once tuned, and do the tuned kernels keep OPP1's linear scaling?

Hypothesis

EXP2 (OPP2 with a and b exchanged) matches OPP2 at 100K × 100K and mirrors it on the lopsided shapes. In parallel both should scale like OPP1, about 15.7×, since the per-thread working set is unchanged.

Background: Amdahl's law

If part of a job can't be spread over threads, that part limits the speedup however many threads work on the rest. With a fraction s of the one-thread time serial, t threads give at most 1 / (s + (1 − s)/t).

Here the serial part is building the four copies of the long polynomial, which takes about 17–21 ms. On one thread that is 7% of 302 ms and goes unnoticed. On 16 threads the multiply shrinks to 17 ms while the copies still take 16.5 ms, half of the total.

Conclusions

Supported, with one identified exception. Building the shifted copies in parallel (or only for each thread's own window) is the obvious next step and has not been done.

Final configurations

  • OPP1 / EXP1 (linear-speedup goal): output ownership, one contiguous work-balanced range per thread with edges on cache lines, blocks of 2,048 outputs inside each range. 15.6–15.8× at 16 threads at all three shapes.
  • OPP2 / EXP2 (single-core TPP goal): OPP1's structure, R = 8 unroll-and-jam, four aligned shifted copies of the inner operand, U = 3 interleaved accumulators, FMA chain kept, block 1,024. 80.8% TPP on one E-core.

The most useful things learned

  1. Which polynomial is the inner loop decides which cache level the loop runs from, and changes OPQ/EXQ speed by up to 3.7× at equal work.
  2. Reducing over full-length private copies of c scales only per cluster (≈ 46 GFLOP/s). Owning contiguous slices of the output, walked in L1-sized blocks, removes the race, the reduction and the cluster limit together.
  3. How the output is split matters as much as whether it is split: many small dynamically-dealt blocks cost coherence traffic at every boundary; t contiguous balanced ranges do not.
  4. On an E-core every 256-bit load, store and broadcast is two µops. The single-core limit is vector loads per FMA; unroll-and-jam brings it to (R + 1)/R, and the one attempt to get below one was slower.
  5. Two compiler details were each worth 15–20%: -ffast-math reassociation broke the FMA chain into mul/add, and GCC folded loads into FMAs and undid a hand-written register tile.
