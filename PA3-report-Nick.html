PA3 Report: Blocking the Outer Product

Name: Nick Hinderer  ·  Date: 2026-10-20  ·  Machine: barracuda (i9-13900K, E-cores only, Turbo off)

Starting Point

The kernel is c[i+j] += a[i] * b[j] over the whole (i, j) rectangle. The starting code is OPQ, the outer-product loop nest from PA2 (i outside, j inside), copied unchanged into this project as 01-OPQ. Unless stated otherwise, timing is at 100,000 × 100,000 (1010 multiply-adds, 20 GFLOP), on E-core 16 for one thread and E-cores 16–31 for more. Peak (TPP) is 35.2 GFLOP/s per E-core. Every version passed the shared gate (42 oracle cases, 14 gold cases, sequential and parallel binaries) before it was timed, except the deliberately racy builds of Experiment 11.

OPQ: 9.41 GFLOP/s (median of 5, --record-seq), 26.7% of TPP, the same as in PA2.

BKQ is built in the three steps the project describes, each timed on its own: block the outer loop, block the inner loop, then interchange loops. The block size is a runtime knob (--tune block_size), so one build covers a whole scan, and blocks are square. The sources are kept in 03-BKQ/attempts/.

Experiment 1: block the outer loopsequential

Question

Does cutting OPQ's outer loop into blocks change anything by itself?

Hypothesis

No. The additions happen in exactly OPQ's order, and every row still sweeps all of b. The rate should be 9.4 GFLOP/s at every block size, within 2%.

Experiment Design

for (ii = 0; ii <= dA; ii += bs)                  /* blocks of bs rows */
    for (i = ii; i <= min(ii + bs - 1, dA); i++)
        for (j = 0; j <= dB; j++)
            c[i + j] += a[i] * b[j];
Background: what blocking a loop means

Blocking (also called strip-mining) cuts one loop into two: an outer loop that steps from block to block, and an inner loop that runs through one block. On its own it changes nothing: the same iterations run in the same order, only counted differently.

It becomes useful when another loop is then moved between the two new ones. That reorders the work so that a small piece of data is used many times before the program moves on, and a small piece can stay in the fastest cache. Steps 1 and 2 only prepare for that; step 3 makes the move.

Block sizes 64, 256, 1,000 and 4,096; 3 reps each; sweep.sh --threads 1 --tune block_size=….

Experiment 2: block the inner loop as wellsequential

Question

What does blocking the j loop inside each row do, before any loops are interchanged?

Hypothesis

The order of the additions is still OPQ's, and each row still sweeps all of b, now in pieces, so there is no cache gain. Large blocks should run at OPQ's rate. Small blocks should be slower, because each piece is a short vector loop with its own start-up and leftover elements: noticeably slower at 64 (a guess of 20–40%), and back to OPQ's rate by about 512.

Experiment Design

for (ii = 0; ii <= dA; ii += bs)
    for (i = ii; i <= min(ii + bs - 1, dA); i++)
        for (jj = 0; jj <= dB; jj += bs)              /* the row, in pieces */
            for (j = jj; j <= min(jj + bs - 1, dB); j++)
                c[i + j] += a[i] * b[j];

Experiment 3: interchange the loops (tiles)sequential

Question

Moving the jj loop outside the i loop makes the program finish one square tile, bs rows by bs columns, before it starts the next. Does that keep the data in L1, and for which block sizes?

Hypothesis

While a tile runs, each row reads b[jj … jj+bs−1] (4·bs bytes) and updates a window of c that slides by one element per row. Over the whole tile c spans 2·bs elements (8·bs bytes), so the tile's footprint is about 12·bs bytes, and the 32 KB L1 holds it up to bs ≈ 2,700. Prediction: from bs ≈ 256 to ≈ 2,000 the rate rises above OPQ's 9.4 to about the rate OPQ reached in PA2 when its inner loop fit in L1 (12.6–13.2), peaking around 13 GFLOP/s somewhere in 512–2,048. Above ≈ 2,700 it falls back to about 9.4. Small blocks (≤ 128) stay below the peak because of loop overhead.

Experiment Design

for (ii = 0; ii <= dA; ii += bs)                  /* tiles, row by row */
    for (jj = 0; jj <= dB; jj += bs)
        for (i = ii; i <= min(ii + bs - 1, dA); i++)  /* one tile */
            for (j = jj; j <= min(jj + bs - 1, dB); j++)
                c[i + j] += a[i] * b[j];
Background: why finishing a tile first helps the cache

In OPQ every row sweeps all 100,001 values of b and a 100,001-long stretch of c, 800 KB in all. By the time the next row starts, the start of that data has been pushed out of the 32 KB L1, so every row fetches it again from L2.

In a tile, each row touches only bs values of b and bs values of c, and the next row of the same tile uses the same values of b and all but one of those values of c. If that data fits in L1, it is fetched from L2 once per tile instead of once per row.

15 block sizes from 64 to 8,192, including values that are not powers of two (96, 192, 384, 768, 1,000, 1,536, 3,000); 3 reps each.

Experiment 4: which interchanges mattersequential

Question

With tiles in place there are two more orders to choose: the order the tiles are visited (row by row or column by column), and the order of the two loops inside a tile (i then j, or j then i). Do they change anything?

Hypothesis

At block size 512, where a tile's data fits L1 comfortably, both choices change the rate by less than 3%: each tile's data fits L1 whatever order the tiles come in, and for a square tile the two inner orders are mirror images. At 4,096, where a tile's row data just fills L1, what the next tile can reuse may matter; visiting tiles column by column, so consecutive tiles share the same block of b, should be at least as fast as row by row. Low confidence for 4,096; the inner order again within 3%.

Experiment Design

Compile-time switches in step3_tiles.c: OUTER (0: for ii { for jj }, 1: for jj { for ii }) and INNER (0: for i { for j }, 1: for j { for i }). All four combinations at block sizes 512 and 4,096, 3 reps.

Experiment 5: the dip at 768–1,024sequential

Question

Plain tiles of 768–1,024 run about 5% slower than both 512 and 1,536–3,000 (Experiment 3). Their data fits L1 at every one of these sizes, so why?

Hypothesis

Formed from Experiment 3's numbers, before any of the runs below. The tile loop compiles to 6 instructions per 8 elements (load b, FMA with c from memory, store c, add, compare, branch), and each row of a tile runs it bs/8 times. Converted to cycles per row, the dip is about the same at every block size above 512: 15.9 cycles at 768, 15.4 at 1,024, 13.7 at 1,536, 12.4 at 2,048, 10.5 at 3,000. A fixed cost per row that appears only above 512 looks like one mispredicted branch per row, the loop's exit. Hypothesis: the branch predictor learns the exit of a loop that runs up to about 64 times in a row, but not one that runs 96 or more.

  • Counters: about 0 mispredicted branches per row at block sizes up to 512, about 1 from 768 on. Split loads, 4K-alias load blocks and L1 misses per FMA flat across 512–1,024.
  • A finer scan: a drop of about 5% somewhere between 512 and 768 (64–96 iterations), then a slow recovery as the cost spreads over longer rows; 12–16 cycles per row.
  • The same loop unrolled twice runs half as many iterations per row, so the dip should move to twice the block size: 768–1,024 back at the 512 level, the drop between 1,024 and 1,536.
Background: why the last pass of a loop can cost a mispredict

A core guesses the outcome of every branch before it is computed and keeps working on the guess. A loop's closing branch goes back to the top every time except the last. To guess the last one right, the predictor has to recognize where it is in the count, from its record of the branches just taken. When it can't, it guesses "go back" once too often, starts another pass, and has to throw that work away when the comparison comes through.

In a tile that happens once per row, so its cost is a fixed number of cycles per row whatever the block size. Spread over a longer row, it matters less.

  • Counters for step 3 (report/scripts/pc_branch.sh, E-core 16, 3 reps): mispredicted branches and cycles per row of a tile, and split loads, 4K-alias load blocks and L1 misses per FMA, at 8 block sizes from 256 to 2,048, and for the unrolled loop at 512–2,048. Six more block sizes between 656 and 752 were added after the fine scan showed 736 at the full rate.
  • Fine scan of step 3: block sizes 448–1,024 in steps of 32 (56–128 iterations per row), 3 reps.
  • Unrolled twice: attempts/step3_unroll2.c is step 3 with #pragma GCC unroll 2 on the innermost loop, which then handles 16 elements per pass. Block sizes 256–4,096, 3 reps.

Experiment 6: inside a tile, one technique at a timefine grain

Question

The tiled loop of Experiment 3 still runs OPQ's statement row by row: two 256-bit loads per FMA (one of b, one of c) and a store. An E-core starts one 256-bit load per cycle, so that loop cannot pass 50% of TPP however well its data fits in cache. How much do the single-core techniques from PA2 give inside a square tile, and what does each one contribute?

Hypothesis

The techniques are the ones that took PA2's OPP2 from 14.0 to 28.5 GFLOP/s, so the predictions lean on those measurements. The order should be the same: each technique adds to the one before. Experiment Design

One source, 03-BKQ/attempts/opt_tile.c: the tiles of Experiment 3 visited row by row, with the inside of a tile rewritten. Each technique is a compile-time switch, so its effect can be measured on its own:

  • R, unroll-and-jam. R rows of the tile are handled together and their inner loops fused, so each vector of c is loaded once, receives R FMAs, and is stored once. This is what removes the load of c from almost every FMA, and the only technique here that changes the 50% limit: with R = 8 it becomes 9 loads per 8 FMAs, 89%.
  • U, interleaving. U vectors of c are handled at once and their FMAs alternate, so U independent chains of FMAs are in flight instead of one. Without it each vector's R FMAs wait for each other.
  • Aligned copies. Four copies of b, shifted by 0–3 floats, so every row reads its window from a copy where the window starts on a 16-byte boundary and no load splits a cache line.
  • Chain kept. The row loop is compiled without -fassociative-math, so the compiler can't regroup each vector's R products into multiplies and adds (in PA2 that turned 8 FMAs into 12 operations).
Background: why one more row per pass doesn't simply mean faster

The R values of a for a group of rows each sit in their own vector register for the whole inner loop, and the U vectors of c being built need registers too. An E-core has 16. A larger R lowers the loads per FMA, (R + 1)/R, but leaves fewer registers for the U chains that hide the FMA's 6-cycle latency. R = 8 with U = 3 uses 11; R = 10 with U = 6 uses all 16.

All at block size 1,024, 5 reps. With the copies a tile's working set is about 24·bs bytes (8·bs of c, 16·bs for the four copies of the b block), 24 KB at 1,024.

Each technique contributes as expected, but square tiles cost far more than the 0.7% the hypothesis estimated. worked out afterwards The ragged ends are the likely reason. Row r of a group reaches outputs c[i0+r+jj … i0+r+jend], so at each edge of the tile there is a triangle of outputs that only some of the R rows reach. opt_tile.c runs those triangles in scalar loops: R(R − 1) = 56 single-element updates per group of rows per tile. That is 0.7% of the work, but a scalar update costs many times its share of a vector FMA. PA2's OPP2 cut its blocks along outputs, not along j, so it had these triangles only at the two ends of the whole product. Experiment 7 tests this.

Experiment 7: tiles without ragged ends (final BKQ)fine grain

Question

Is the scalar handling of each tile's ragged ends what holds the tiled kernel about 10% below PA2's, and how far does removing it go?

Hypothesis

If the triangles are the cause, a version without them should rise from 25.6 to about 28 GFLOP/s at block size 1,024, close to PA2's 28.46. If it stays near 25.6, the explanation is wrong. A block-size scan should peak around 1,024–1,280, where the working set still fits L1, and R = 10 with U = 6 should give 28.5–29.

Experiment Design

The triangles exist because row r of a group stops reaching the tile's outputs r elements earlier or later than row 0. If every row could run over the same range of outputs, the whole group would be one vector loop. So each tile column gets its own copy of its b block with R − 1 zeros on each side (again in four shifted, aligned copies). Each group of rows then runs over the union of its rows' outputs, and a row's terms that fall outside the tile multiply a zero:

padded block for columns jj … jend:   [ 0 … 0 | b[jj] … b[jend] | 0 … 0 ]
                                        R − 1                     R − 1

for k over the union of the group's outputs:      /* one vector loop */
    c[k] += a[i0]   * pad[k - i0 - jj + R - 1]
          + a[i0+1] * pad[k - i0 - 1 - jj + R - 1]
          + …                                     /* out-of-tile terms are × 0 */

The tile stays square and owns exactly its own products: the zeros add nothing, and every write stays inside the tile's own range of c. The price is (R − 1)/bs extra FMAs on zeros, now as vector work. Only two small pieces stay scalar: up to 3 outputs at the start, so that c is read on a 16-byte boundary, and the vector loop's leftover. Block sizes 256–2,048 with R = 8 and U = 3; R = 10 and U = 6 at 1,024; counters for both versions at 1,024.

Background: why multiplying by zero is cheaper than not multiplying

Skipping the out-of-tile terms sounds cheaper than computing them and adding zero. But a vector instruction does 8 elements at the same cost as 1, and the skipped terms are scattered: a few at each end of each row. To skip them the code has to fall back to one element at a time for those stretches.

Computing them against zeros keeps every row in the same 8-wide loop. Here that wastes about 0.7% of the arithmetic and saves far more than it wastes.

Experiment 8: using each window of b twicefine grain

Question

Experiment 7's kernel is held at 1.125 loads per FMA: every row of a group reads its own window of b for every vector of c. But rows t and t + 8 of a group read the same windows, one vector apart. Can a kernel that loads each such window once and uses it twice get below one load per FMA, and does that bring it closer to TPP?

Hypothesis

For R rows per group and U vectors of c per pass, sharing leaves 8U + (R − 8) window loads and U loads of c per R·U FMAs: 0.86 per FMA for R = 12, U = 3, instead of 1.125. The registers limit how far this goes: R broadcasts of a, U vectors of c and one window must fit in 16. Two ways of looking at it gave different predictions, written down before any run:

  • Loads. Below one load per FMA the FMA unit becomes the limit, 1.0 cycle per FMA. With the same overhead outside the main loop as BKQ (0.09 cycles per FMA), R = 12, U = 3 would run at about 32 GFLOP/s, 91% of TPP.
  • Latency. An FMA's result takes 6 cycles, so about 6 chains of FMAs must be in progress at once. Experiment 6's D (one chain of 8 FMAs per pass) ran at 1.60 cycles per FMA, far above its load floor of 1.125, so the core can't look far ahead. A toy model (report/model/rs_sim.py) holds the FMAs waiting in a scheduler of C entries, in program order, and issues the oldest ready one each cycle. With C = 12–13 it reproduces D. Run on the order of FMAs GCC actually emitted for each configuration, it gives R = 12, U = 3 about 1.42 cycles per FMA: each pass has only 3 chains, each 12 FMAs long, and a window of 13 can't see past them.

Prediction: the latency view. Cycles per FMA = the larger of the load floor and the model, plus 0.09. No configuration beats BKQ. With 12 rows, about 23–24 GFLOP/s whether windows are shared or not; with more chains per pass (U = 5), back to about BKQ's 29. If R = 12, U = 3 lands near 32 instead, the load view is right and the model is wrong.

Background: why longer chains need more room to wait

Each vector of c in a pass gets one FMA per row of the group, each needing the result of the one before. With 8 rows that is a chain of 8 FMAs, 48 cycles long at 6 cycles each. The FMA unit can start a new FMA every cycle only if it always has one whose input is ready, which takes about 6 chains in progress at once.

A pass offers U chains. The core can work on the next pass's chains too, but only if those FMAs have already reached its scheduler, which holds a limited number of waiting instructions. Longer chains (more rows) keep each pass's FMAs waiting longer, and fewer chains per pass (fewer vectors, because the rows took the registers) leave less to choose from.

Experiment Design

03-BKQ/attempts/opt_tile_reuse.c, built from Experiment 7's kernel. The window that row t reads for vector u is the window row t + 8 reads for vector u + 1, because row t + 8's pointer into the shifted copies is row t's minus 8. Each step of a pass handles rows t and t + 8 together:

for t = 0 … 7:                                   /* rows t and t + 8 */
    c0 += a[t+8] · window(t, −8)                 /* row t + 8, vector 0: its own window */
    for u = 0 … U−1:
        w = window(t, 8u)                        /* loaded once */
        c_u     += a[t]   · w                    /* row t,     vector u     */
        c_(u+1) += a[t+8] · w                    /* row t + 8, vector u + 1 */

Left to itself, GCC folds the window's load into both FMAs that use it, which loads it twice again. So the timed build writes the pass with GCC vector types and keeps the shared window in a register with an empty asm statement; the checking build does the same steps in the same order, one element at a time with BPM_ACC. Since the two builds now differ in more than the accumulation, both checks matter: a window offset bug planted in the timed path only is missed by the gate and caught by the timed-build check (99 failing configurations); planted in the checking path only, the gate catches it (4 gold cases) and the timed-build check does not.

Part B: spreading the tiles over cores

From here on, different cores run different tiles, and inside every tile each core runs the BKQ kernel of Experiment 7 unchanged. The question is which tiles may run at the same time. Two tiles race if they add into the same element of c, and what a tile adds into follows directly from its position.

Tile (I, J) covers rows I·bs to I·bs + bs − 1 and columns J·bs to J·bs + bs − 1, so its outputs c[i + j] run from

(I + J)·bs   to   (I + J + 2)·bs − 2

That range depends only on D = I + J, the tile's anti-diagonal in the grid of tiles:

  • Same D: exactly the same range. They race, however far apart they are in the grid.
  • D one apart: half the range in common. They race.
  • D two or more apart: no common element. They are safe together.

So inside one column of tiles (or one row), a tile races only with the tiles directly above and below it (or left and right of it). Across the whole grid it races with every tile whose D is within 1 of its own. The variants handle this in different ways: by giving every thread a private copy of c (BKP1), by handing out whole anti-diagonals (BKP2), by one column of tiles at a time (BKP3), and by leaving the order to OpenMP task dependences (BKP4, Experiment 12). Every variant keeps the four-loop structure: two loops over tiles (in BKP2 and BKP4 indexed by diagonal D and row I instead of I and J) around the two loops of a tile, which are BKQ's kernel. All use block size 1,280 unless stated, so the grid is 79 × 79 tiles at 100K × 100K. All are checked by the gate at 16 threads and by the timed-build check at 1, 3 and 16 threads. Schedules built to race fail those checks (Experiment 11), so the checks can see a race when there is one.

Background: what a race does here

Adding into c[k] is three steps: read the old value, add, write the new value. If two threads do this to the same element at the same time, both can read the same old value, and the second write throws away the first thread's addition. Nothing crashes; the answer is just wrong, by a different amount on every run. Two tiles race exactly when their ranges of c overlap and they run at the same time.

BKP1, reduction. The loop over rows of tiles is split among the threads, and every thread adds into its own private copy of c:

#pragma omp parallel for schedule(static) reduction(+:c[:n])
for (I = 0; I < nI; I++)                      /* rows of tiles */
    for (J = 0; J < nJ; J++)
        tile(I, J);                           /* BKQ's kernel */

Inside the loop c is the thread's private copy, at a different address from the real c, so each thread works out its own 16-byte alignment for the kernel.

BKP2, anti-diagonals. Each diagonal D = I + J belongs to one thread, which runs its tiles one after another. Diagonals two apart never overlap, so all even diagonals can run together, and after a barrier all odd ones:

#pragma omp parallel
for (parity = 0; parity < 2; parity++) {
    #pragma omp for schedule(dynamic, 1)       /* barrier at the end */
    for (q = 0; q < count[parity]; q++) {      /* diagonals of this parity, longest first */
        D = order[parity][q];
        for (I = max(0, D - nJ + 1); I <= min(D, nI - 1); I++)
            tile(I, D - I);
    }
}

Diagonals hold from 1 tile up to 79, so the long ones are handed out first; the short ones then fill the gaps at the end of each phase.

BKP3, columns. One column of tiles at a time. Inside a column a tile overlaps only the tiles directly above and below it, so the even tiles run together, then the odd ones. Neighboring columns never run at the same time, which matters, because tile (I, J) also overlaps (I − 1, J + 1) and (I + 1, J − 1):

#pragma omp parallel
for (J = 0; J < nJ; J++)
    for (parity = 0; parity < 2; parity++) {
        #pragma omp for schedule(static)       /* barrier at the end */
        for (I = parity; I < nI; I += 2)

Background: why whole tiles make a staircase

A static schedule decides each thread's share before the loop starts, and a share is a whole number of tiles (or rows of tiles). If 79 rows go to 16 threads, 15 threads get 5 rows and one gets 4, and the run ends when the threads with 5 are done: 79 rows of work take as long as 80. With 13 threads one thread gets 7 rows and the rest get 6, so the run still takes as long as 7 rows, exactly as with 12 threads. Adding a thread only helps once it lowers the largest share, so the speedup climbs in steps.

A dynamic schedule hands out work as threads become free, so a thread that is done early takes another piece. With many small pieces left at the end, everyone finishes at about the same time.

Background: task dependences

A task declared with depend(inout: x) may not start until every earlier task (in the order the tasks were created) that also named x has finished. Tasks that name nothing in common are free to run at the same time, on whatever threads are free.

Here x is not data the task touches but a stand-in: seg[s] stands for segment s of c, the elements s·bs to s·bs + bs − 1. Tile (I, J) writes all of segment D = I + J and all but the last element of segment D + 1, so it names both. Two tiles name a common segment exactly when their ranges of c overlap, so the dependences encode the race condition of the Part B design and nothing more.

Experiment Design

#pragma omp parallel
#pragma omp single                                /* one thread creates the tasks */
for (q = 0; q < nD; q++) {                        /* even diagonals longest first, then odd */
    D = order[q];
    for (I = Ilo(D); I <= Ihi(D); I++) {
        #pragma omp task firstprivate(I, D) depend(inout: seg[D], seg[D + 1])
        tile(I, D - I);
    }
}                                                 /* the region ends when all tasks have run */

Within a diagonal every tile names the same two segments, so the tiles of a diagonal run one after another. Even diagonals share no segment, so they all start at once. Odd diagonal D names segments D and D + 1, last named by the even diagonals D − 1 and D + 1, so it starts when those two have finished, without waiting for the rest of the even phase. Conclusions

Partly supported. The kernel itself loses nothing at 16 threads: the tiles stay in each core's L1. Experiment 14: lopsided shapessequential + coarse grain

Question

Everything so far is 100K × 100K, where the tiles form a square 79 × 79 grid. What happens to BKQ and the parallel schedules when the product is lopsided, 4,000,000 × 1,000 (TA) or 1,000 × 4,000,000 (TB), the shapes PA2 used? Both are 8 GFLOP.

Hypothesis

  • BKQ alone. TA is a single column of 3,126 tiles, each 1,280 × 1,001: about BKQ's usual rate, 28.5–29.2 GFLOP/s. TB is a single row of 3,126 tiles, and BKQ builds four padded copies of every one of their b blocks (65 MB) on one thread before any tile runs: 26.5–27.5, the copies taking 7–10% of the time.
  • Serial setup is Amdahl's serial part. With 16 threads the tiles take about 18 ms. At TB the copies and zeroing c take 20–30 ms on one thread, so BKP2 should reach only 6–8× BKQ, and 13–15× once the setup is split among the threads (PARPREP=1). At TA the setup is mostly zeroing c (16 MB): 12–13.5×, then 14.5–15.3×.
  • The shape of the grid decides some schedules. BKP3 runs a column at a time, so at TA (one column of 3,126 tiles) it does as well as BKP2, and at TB (3,126 columns of one tile) it runs one tile at a time with two barriers per tile: about 1×, or below. BKP2 and BKP4 deal out diagonals, which exist in either orientation; BKP4 within 5% of BKP2.
  • The reduction runs out of stack. Each of BKP1's private copies of c is 4,001,001 floats, 16 MB, and lives on its thread's stack, over the default limit: BKP1 should crash at both shapes. With the stacks raised (ulimit -s, OMP_STACKSIZE=128M): the static split of rows of tiles at TB (one row) about 1×; the others 4–6×, held back by merging 16 copies of 16 MB.

dA = 4,000,000, dB = 1,000 (TA) and the reverse (TB), block size 1,280. Every variant records its own one-thread baseline at each shape. BKP2: threads 1–16 with PARPREP 0 and 1. BKP3 and BKP4: 16 threads, PARPREP 0 and 1. BKP1: 16 threads with the default stack first, then with the stacks raised, static and collapsed. 3 reps (BKQ 5).

What was learned

  1. Blocking a loop changes nothing until another loop is moved inside the blocks. Moving jj outside i turns the loop nest into tiles, keeps each tile's data in L1, and gives 42% over OPQ. It works up to the block size where a row's data (8·bs bytes) fills the 32 KB L1, about 4,096. After that, neither the order of the tiles nor the order inside a tile made a measurable difference.
  2. The plain tiles' dip at 768–1,024 is a branch, not the cache: once a tile's row loop runs more than about 80 times, its exit is mispredicted on every row for most loop lengths, about 16 cycles each. Unrolling the loop twice moves the dip to twice the block size.
  3. Inside a tile the single-core techniques add up as they did in PA2, each measured on its own: unroll-and-jam +45%, aligned copies +6%, keeping the FMA chain +12%, interleaving +16%. Square tiles cut every group of rows at both edges of every tile; padding each block of b with zeros keeps the whole group in one vector loop: 29.27 GFLOP/s, 83% of TPP.
  4. BKQ is held at 1.125 loads per FMA, and the obvious way below it, loading each window of b once for two rows, does not pay on these cores. With 16 registers, more rows per group leave fewer and longer FMA chains, and the waiting fills the scheduler or the register file. The best such kernel only matches BKQ.
  5. Which tiles race is decided by I + J alone. Within one row or column that reduces to "only the immediate neighbours"; across the grid it does not, and a checkerboard built on the neighbour rule is both wrong and slow. The gate and the timed-build check caught every racy schedule tried.
  6. The kernel loses nothing on 16 cores: the time spent in tiles is within 0.5% of the one-core time. What is lost is outside the tiles: whole tiles dealt statically (staircases), whole diagonals dealt dynamically (3.7% at block size 1,280, 0.5% at 1,024), setup left on one thread (0.4 ms, or 1 ms when its memory still has to be faulted in) and the reduction's merge (1 ms). Choosing the block size for 16 threads gave the best result: 457.8 GFLOP/s, 81% of TPP.
  7. Barriers are cheap (2–3%). What race-freedom costs is how finely the work can still be dealt: BKP3's half-columns cost 16.5%. Task dependences on segments of c state the race condition directly and reach 15× without a reduction or barrier.
  8. Lopsided shapes separate the strategies. The reduction's private copies of c must fit on the threads' stacks and take longer to merge than the work; a column schedule needs many tiles per column; and setup left on one thread becomes Amdahl's serial part (8.3×, then 13.6× once split, at 1,000 × 4,000,000).

Open items

  • The branch predictor gets the loop exit right at 90–94 iterations but not at 82–88 or 96 and above; why is not known. Neither is why 4K-alias load blocks double whenever the exit is mispredicted.
  • At 1,000 × 4,000,000 the tiles run 5% slower than at 4,000,000 × 1,000; not measured why.
  • BKP4 waits about twice as long as a simple model of its task graph predicts; the rest is not separated.
  • The remaining distance to TPP is mostly inside the tile (BKQ at 83% of one core's TPP). No way below one load per FMA was found that fits in 16 registers.

Notes on method

  • All measurements 2026-10-20 on barracuda (i9-13900K, Turbo off), with no other users logged in and every E-core under 1% busy before and after each batch (report/scripts/ecore_idle.sh); one timing job at a time; sequential runs on E-core 16, parallel runs on E-cores 16–31 with _gate.sh's cluster-cyclic placement. Builds and checks of new code ran on char, an identical machine, never alongside a timing run.
  • Experiments 1–4, 6, 7, 9 and 10 were first run on tuna while other users were active, then repeated on barracuda. The repeats agree within 0.4% on one core and within 1% at 16 threads, except BKP1 at 10 threads (5% higher; tuna's reps there spread 4.8%). The tables show the barracuda runs. Hypotheses were written before the first runs, in a lab log with the time (report/LOG.md); where a hypothesis quotes an earlier result, it quotes the first run.
  • A 16-thread rate measured as part of a 1–16 sweep and one measured by a run of the 16-thread case alone can differ by about 1.5%, because the second takes page faults in its setup on every call. Comparisons in this report use the same kind of run on both sides.
  • Counters: perf stat --cputype cpu_atom, user mode, divided by vector FMAs of useful work. The small models used to explain results after the fact are in report/model/.
  • collect.py does not keep a build's build_params in the csv; the builds with switches were checked to report them when run. plot.py needs xlsxwriter, which is not installed on these machines; a virtual environment for it is in PA3/report/.venv.
